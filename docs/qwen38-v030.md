# Qwen3.8-Flash-Next on vLLM 0.30

`qwen38-v030` is a separate single-Spark trial of vLLM 0.30.0 with the
same NVIDIA checkpoint used by `qwen38`. Its API model ID is
`qwen3.8-flash-next-v030`. The existing `qwen38` recipe remains available for
comparison and rollback. Both local thinking and fast acceptance suites
passed; the performance and long-context checks are recorded below.

The runtime follows the v0.30 lane of
[MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark/tree/b8439110eec0230facbe4ddf0dffe01b8f769be0)
at `b8439110eec0230facbe4ddf0dffe01b8f769be0`. Its official vLLM base is pinned
by digest, with three upstream patch generators producing four installed
modules. This is a patched vLLM 0.30 runtime; it does not reuse the old
recipe's model overlays.

## What the trial changes

The official checkpoint keeps NVIDIA's published weight quantization and
multimodal assets. The runtime backports FP8 QSA KV support, uses a persistent
file for the large PLE embedding table, and restricts MTP draft proposals to
47,172 vocabulary IDs. The target model still verifies draft proposals with
its full vocabulary. The reduced draft vocabulary is a serving optimization;
it does not rewrite the checkpoint.

The initial settings are a native 262,144-token context, TP1, four sequences,
2,048-token prefill batches, MTP3, FP8 KV, a fixed 12 GiB KV allocation, and
separate runtime caches. Prefix caching is enabled, with aligned Mamba state,
MTP index sharing, and trailing prefix-cache block dropping disabled as in
the upstream lane. The latter is experimental and can affect speculative
acceptance. Exact settings belong in
`[models.qwen38-v030]` and its `env` / `vllm` sections in the catalog. Context
and sequence ceilings do not reserve a full context for every simultaneous
request. The initial trial does not extend context with YaRN or apply runtime
abliteration.

The local trial explicitly uses `--mamba-ssm-cache-dtype float32`, preserving
the existing recipe's recurrent-state precision. This differs from the
upstream v0.30 environment's BF16 recurrent state. FP8 attention KV and FP32
recurrent state are separate settings. The upstream BF16 timings therefore
do not describe this exact local configuration; any memory or speed impact
of keeping FP32 must be measured here.

The old `qwen38` runtime also uses this NVIDIA snapshot, FP8 KV and MTP3, but
uses older model overlays, a 65,536-token draft vocabulary and a different
PLE loading path. A successful trial would establish compatibility and a
local performance comparison; API smoke tests alone do not establish equal
model quality across these runtime paths.

Text, images, separated reasoning, automatic tool calls and structured JSON
are intended capabilities. The parsers are `qwen3` for reasoning and
`qwen3_coder` for tools. Thinking defaults on and can be disabled per
request with `chat_template_kwargs: {"enable_thinking": false}`. Qualification
below includes a still-image fixture, strict JSON, a synthetic tool round trip
and concurrency. It does not qualify video or the entire context window.

The [upstream v0.30 report](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark/blob/b8439110eec0230facbe4ddf0dffe01b8f769be0/README.md#vllm-030-agentic-lane-start-v030sh-opt-in)
reports 36.8 tokens/s prose and 54.5 tokens/s code at concurrency one, plus
2,140 prompt tokens/s on a 47K prompt. Its comparison uses the author's
different default checkpoint, so those figures do not predict a gain over
our existing NVIDIA recipe. The author also reports three successful needles
in a 200K prompt and a one-hour, 784-request mixed workload without server
errors. These remain upstream observations until repeated locally.

## Prepare and start

```sh
./spark-serve pull qwen38-v030 --node head
./spark-serve up qwen38-v030 --node head --no-hermes --json
./spark-serve status --json
```

Preparation reuses and fully authenticates the cached NVIDIA snapshot at the
same revision. It requires no second checkpoint download when all files are
already present and correct. It builds a separate image and cache namespace.
Preparation does not start a GPU workload or stop the ongoing GLM preparation.

Startup authenticates all checkpoint files before replacing the selected
node's current serving workload. Normal Hugging Face snapshot links into the
corresponding blob cache are supported. Missing, modified or additional
serving files fail preflight. Allow time to hash approximately 133 GB.

The first model start creates a separate file-backed PLE table of about
47.7 GiB in the v0.30 cache directory. This derived runtime file requires extra
disk space even though the checkpoint itself is shared. It is retained for
later starts; upstream reported approximately 14 minutes for the first boot
and 12 minutes for a subsequent boot. Those timings are not local readiness
guarantees. Verify startup logs identify the expected checkpoint and show
whether the PLE table was built or reused.

This entry has one model rank. If the current model spans both Sparks,
switching to this entry must first release that distributed allocation.
Keep `--no-hermes` during the trial so the client's existing selection is not
changed as part of startup.

## Acceptance commands

Run these from the Mac after the head is ready. Replace the hostname if the
private catalog uses another head. The existing Qwen runner accepts the new
served ID unchanged; generated code and tool calls are never executed.

```sh
python3 tools/qwen_acceptance.py \
  --url http://sparkone.local:8000/v1 --model qwen3.8-flash-next-v030 \
  --thinking --timeout 600 --concurrency \
  --output diagnostics/qwen38-v030/acceptance-thinking

python3 tools/qwen_acceptance.py \
  --url http://sparkone.local:8000/v1 --model qwen3.8-flash-next-v030 \
  --no-thinking --timeout 600 --concurrency \
  --output diagnostics/qwen38-v030/acceptance-fast

python3 tools/qwen_benchmark.py \
  --url http://sparkone.local:8000/v1 --model qwen3.8-flash-next-v030 \
  --samples 2 --timeout 180 --deadline-seconds 600 --concurrency \
  --output diagnostics/qwen38-v030/benchmark-fast
```

The acceptance runner checks streamed content, finish markers, token usage,
strict JSON, tools, image recognition, summarization, coding syntax, arithmetic
and retrieval. The default retrieval prompt is approximately 8K tokens and
requires at least 6K actual server-reported prompt tokens. More ambitious
retrieval runs should report the actual token count rather than equating a
configured 262K limit with a passed 262K test.

The speed runner explicitly disables thinking. It runs a warmup, two samples
each of prose/coding/reasoning prompts, and two simultaneous requests. Sample
responses allow 768 output tokens. Rates include response overhead; estimated
post-first-output rates can be affected by multi-token speculative streaming
deltas. Prefix reuse and short response lengths can affect this small sample.
Compare the same prompts, request modes and token budgets between recipes.

## Local results

Preparation, the first cold startup, and both acceptance modes passed on
head on 2026-09-27. These are synthetic capability checks, not a broad model
quality evaluation. A short speed sample and a 230,110-token retrieval also
passed. The
[startup receipt](../diagnostics/2026-09-27-qwen38-v030/startup-summary.json)
records effective runtime settings and timings; the
[full container log](../diagnostics/2026-09-27-qwen38-v030/startup-container.log)
retains their source evidence.

vLLM reported 76.59 GiB for model loading, a fixed 12 GiB FP8 KV pool with
722,804 token capacity, and estimated 2.76 concurrent full-length 262,144-token
requests. This is a capacity estimate, not a tested concurrency result.
FP32 aligned recurrent state selected 3,200-token attention blocks. Prefix
caching, MTP3 with 47,172 draft IDs, and CPU PLE offload were active; async
scheduling was disabled. The engine used `modelopt_mixed`, `FLASHINFER_CUTLASS`
for NVFP4 experts, and `DEEPGEMM` for the FP8 MTP. Graph capture reported
one second and 0.22 GiB. The draft model uses text-only draft inputs during
multimodal requests; image handling remains in the target model.

concurrency at the full context limit. The worker had no model container

The [September 13 baseline](qwen38-nvfp4.md#local-qualification-2026-09-13) for the old
NVIDIA recipe passed 10/10 thinking checks and a 230,110-token retrieval.
The new short sample does not demonstrate a speed advantage over that
historical run:

Both samples used two requests per category with thinking disabled, but this
is a historical comparison rather than a fresh matched A/B test. Generated
outputs and token counts differ, and repeated prompts may benefit from
prefix caching. The local v0.30 recipe retains FP32 recurrent state, unlike
the upstream author's BF16 speed report. No throughput claim is established
for long prompts or sustained concurrent load.

## Roll back

```sh
./spark-serve up qwen38 --node head --no-hermes --json
```

This selects the existing runtime and its original settings while reusing the
same checkpoint. Confirm readiness and `/v1/models` before changing clients.
The original recipe's preparation steps and qualification receipts are in
[qwen38-nvfp4.md](qwen38-nvfp4.md).
