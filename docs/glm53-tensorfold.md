# GLM-5.3-Flash EXL3 on two Sparks with TensorFold

This integrates [MiaAI-Lab's recipe](https://mia-ai.net/models/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold)
as `glm53-tensorfold`. Spark Serve starts and owns both containers through its
normal fenced lifecycle. The existing `glm53-exl3` vLLM recipe is separate.

| Setting | Catalog default |
|---|---|
| Sparks / tensor parallel | 2 / 2 |
| Served model | `GLM-5.3-Flash-EXL3` |
| Engine | TensorFold v0.6.0 with the pinned MiaAI-Lab patch set |
| Target | `Mia-AiLab/GLM-5.3-Flash-EXL3-4bpw-TensorFold` |
| Draft | `incoai/GLM-5.3-Flash-DFlash2` |
| Context per request | 1,048,576 tokens |
| Concurrent streams | 4; configurable from 1 to 8 |
| KV / dense weights | FP8 / q4 |
| API | Cluster head, `cluster.port` (normally 8000) |
| Rendezvous | Head's fabric address, port 29551 |
| Inputs | Text, images and video; remote media URLs disabled by default |

## Prepare and start

Merge `[models.glm53-tensorfold]` and its `tensorfold` section from
`models.example.toml` into a private catalog. The app lists it after Refresh.
Both Sparks must already have Docker with NVIDIA runtime, working key-based
SSH, a connected RoCE fabric, and the fabric settings in `[cluster.nccl]`.
Preparation uses the head's configured QSFP interface to copy assets to the
worker; that interface must exist and have one IPv4 address on each Spark.

```sh
./spark-serve pull glm53-tensorfold
./spark-serve up glm53-tensorfold --no-hermes --json
```

Preparation downloads and fully hashes the pinned target and draft on the head,
builds the derivative from an immutable published image, copies the snapshots
and exact image over the fabric, and verifies them on the worker. It leaves
current serving workloads running. Interrupted checkpoint downloads resume.
The target is approximately 176 GB and DFlash2 2.3 GB on each Spark; upstream
budgets about 25 GB for the image, with additional room needed for build layers
and compiled kernels. This checkpoint differs from the older TR3 weights in
`glm53-exl3` and needs its own download.

Start checks both nodes' image identity, installed runtime, full checkpoint
hashes and actual TensorFold argument parser before stopping a workload. It
starts rank 1 first, then rank 0, and requires both owned containers, the exact
served model and the configured context in `/health` before reporting ready.
The first start compiles kernels. Spark Serve does not apply upstream's
automatic context reduction: a smaller effective window fails readiness.

```sh
./spark-serve use --node head --hermes-target local
./spark-serve use --node head --hermes-target spark
./spark-serve stop --node both
```

## Settings and monitoring

The recipe's `tensorfold` table supports `parallel`, `drafter`, `vision`,
`vision_urls`, `thinking`, `max_tokens`, `communication`, `master_port`, and
sampling defaults. Keep `max_num_seqs` equal to `parallel`. More than four
streams uses a 64-row verify window and a larger memory reserve, leaving less
shared KV capacity. `drafter = "mtp"` requires `parallel = 1` and
`max_num_seqs = 1`; it serves using the checkpoint's own MTP head. Preparation
still authenticates both published checkpoints. This integration currently
supports the recipe's FP8 KV and q4 dense defaults.

Only fabric interface, HCA, GID and optional debug settings are taken from
`[cluster.nccl]`; TensorFold uses the upstream four-channel communication
configuration. Runtime tuning and cache paths are generated by the validated
plan. Direct Docker, mount, environment and vLLM overrides are rejected before
a model switch. Three-Spark, NFS, Ablit weights and display-reservation modes
are outside this project's two-node recipe.

Live inference metrics read TensorFold `/health` counters through the existing
monitor. The native app and benchmarks share the head endpoint and show both
physical nodes as one allocation. Some metrics, including TTFT and KV pool
usage, are unavailable in the current monitor adapter.

```sh
./spark-serve bench run --node head --kind decode --concurrency 4 --requests 8 --no-thinking --json
./spark-serve bench run --node head --kind prefill --prompt-tokens 4096 --no-thinking --json
```

## Provenance and qualification

The [source pins](../recipes/glm53-tensorfold/source-pins.json) record upstream
commit `33b50fde06fd7ea604cbc6a663880068ab1e2ee4`, the immutable image digest,
TensorFold revision and runtime inventories. The [checkpoint manifest](../recipes/glm53-tensorfold/model-source.json)
pins target revision `078455ffe6472f9a52fbc1139f58b9db2881b25c` and draft
revision `bf582e4eacc1810f76656d1811693ff6c6737d2a`, including every file's
size and SHA-256. Retained upstream patches and license notices live in the
[recipe directory](../recipes/glm53-tensorfold/).

The recipe is Apache 2.0. The pinned target's
[LICENSE](https://huggingface.co/Mia-AiLab/GLM-5.3-Flash-EXL3-4bpw-TensorFold/blob/078455ffe6472f9a52fbc1139f58b9db2881b25c/LICENSE)
is MIT; the authenticated license file and model card are authoritative for
this checkpoint revision. TensorFold's Apache and earlier MIT notices are
retained. DFlash2 is **CC BY-NC-ND 4.0, non-commercial use only**;
serving with `drafter = "mtp"` avoids using DFlash2. See upstream notices for
the individual components.

Preparation completed on both Sparks on 2026-10-05. All 102 target and draft
files (178,058,596,393 bytes per node) passed full SHA-256 verification. Both
nodes have the identical ARM64 image
`sha256:c4e79cfe9f05d11030cb03cd8069f2ff1beadf6244a56635ffe15c4f1abb3643`.
Runtime verification authenticated 426 installed files and 82 patches; CPU
checks passed for the GLM EXL3 metadata, DFlash2, vision and exact launch parser
arguments for ranks 0 and 1. The [local preparation record](../diagnostics/glm53-tensorfold/preparation-2026-10-05.json)
contains both receipts and confirms existing services were preserved. No model
was launched during preparation.

Distributed GPU serving, tools, vision, long-context quality and performance
qualification remain **pending**. Offline checks also cover provenance,
corruption rejection, argument construction, two-rank preflight, ownership and
readiness. The upstream recipe publishes performance, vision and long-context
results; those are not measurements of this installation. FP8 KV, q4 dense
weights and chunked KDA change arithmetic; exact draft verification does not
make those representations lossless.
