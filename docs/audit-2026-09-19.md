**Spark Serve — design effectiveness, operational effectiveness, and fourth-model research**

Audit date: September 19, 2026. Source baseline: commit `596d070`, with the existing private catalog and untracked local files preserved. Three parallel reviewers covered design, operations, and model research; the primary reviewer checked source evidence, ran the full offline suite, type-checked SwiftUI, and inspected both live hosts. No serving configuration, model, container, or Hermes setting was changed.

This records the audit cutoff before the user authorized implementation. The subsequent
[GLM implementation and qualification record](glm53-nvfp4.md) tracks the deployment.
That work adds pinned NIM preparation and startup, validates wrappers before switching,
checks NIM's extra ports and engine readiness, corrects model-aware Hermes selection,
writes its configuration atomically, and updates the documented test command. Other
findings below remain findings against the audited baseline; this is not a claim that
every audit recommendation has been implemented.

**Judgment: the lifecycle design is substantially effective, but the overall product is only partially effective until status trust, preflight coverage, and operating qualification improve.** The running DeepSeek deployment passed today's connectivity and generation smoke checks. This is evidence of current function, not sustained availability or comparative model quality.

**Fourth-model recommendation: pilot GLM-5.3-Flash NVFP4 on both Sparks.** NVIDIA explicitly supports this hardware combination. Published results justify testing it for coding, agents, and multimodal work; they do not establish that it is better than every installed model on this user's tasks. Preserve the existing three profiles while qualifying it.

The audit interprets DE as whether the controls and interface are capable of achieving their intended objectives, and OE as whether evidence shows them operating successfully. UI usability is included in DE. The user subsequently selected two priorities: **coding and tool use in Hermes**, and **multimodal work and long documents**. The proposed evaluation gives these tracks equal weight; that weighting is an implementation assumption, not an additional user instruction. General reasoning matters through these tasks rather than as a separate leaderboard objective.

**Findings in priority order**

1. **High — DeepSeek can stop both healthy workloads before discovering unusable assets.** DS4 uses a mutable `production-ready` image tag and a Hub repository ID without a pinned snapshot. Its absent `preflight_args` causes the preflight function to return immediately. The controller stops current workloads before calling startup. Qwen and Nemotron already demonstrate the stronger design: pinned assets and offline preflight before disruption. An isolated call against the DS4 catalog confirmed zero preflight SSH calls; no live switch was attempted. Pin the DS4 image digest and checkpoint manifest, validate both nodes and cross-rank equality, and launch the identities that were checked. Evidence: [catalog](../models.example.toml), `models.example.toml:58`; [CLI](../spark-serve), `spark-serve:1393`; [controller](../spark_serve_controller.py), `spark_serve_controller.py:848` and `:877`.

2. **Medium — Failed or reordered status observations can misrepresent service health.** Each GUI refresh launches independently and unconditionally installs its result. A failed JSON decode sets status to nil, while `syncBootState(nil)` preserves an old `.ready` state; fallback logic still renders green/serving. An older slow response can also overwrite a newer one. This concerns failed observation, not a valid JSON report correctly saying an SSH host is unreachable. Preserve a timestamped last-good snapshot, make observation failure visibly Unknown/Stale, bound process time, serialize polls, and reject superseded responses. Source analysis establishes the path; it was not fault-injected into the user's live GUI. Evidence: [SwiftUI](../gui/SparkServeApp.swift), lines 344, 533, 276 and 316. No automated Swift polling/state tests were found.

3. **Medium — The Hermes badge can remain selected for the wrong model.** `_active_client_node` compares only the provider URL. GUI starts intentionally preserve Hermes selection. Replacing Qwen with Nemotron on the same node can therefore leave Hermes requesting Qwen at the unchanged URL, while the panel still displays its Hermes badge. A temporary configuration reproduced the URL-only match. Match provider, served model, and readiness; otherwise show “Hermes needs updating” alongside Use in Hermes. Also write Hermes configuration through a temporary sibling and atomic replacement: the current write truncates the live file. Evidence: [CLI](../spark-serve), lines 633, 1121, 1470; [SwiftUI](../gui/SparkServeApp.swift), line 1206.

4. **Medium — Invalid recipes can fail after the destructive switch begins.** TOML parsing is not full recipe validation. An unknown wrapper is rejected when constructing launch arguments, after the switch callback is entered. A mocked controller reproduced this ordering using `wrapper='vllmm'`; it did not execute remote commands. Compile an immutable per-rank launch plan before draining, including required fields, supported backend, topology, ports, mount mapping, aliases, and agreement between displayed and actual context/parallelism. This is particularly relevant to adding NIM, which the current wrappers do not understand. Evidence: [CLI](../spark-serve), lines 75, 216, 1481; [controller](../spark_serve_controller.py), lines 848 and 877.

5. **Medium — Start can restart an already serving model, and vLLM requests are not drained.** The supplied screenshot shows DeepSeek selected and serving while Start on both Sparks remains enabled. The controller always replaces the allocation, and stop uses `docker rm -f`; unlike YuE, it has no admission closure or active-request drain. Clicking Start can interrupt long inference and incur a cold start. Make Start idempotent for the same healthy launch plan, expose Restart model explicitly, and implement bounded request drainage with explicit force behavior. Until then, disclose interruption in the action. Evidence: [SwiftUI](../gui/SparkServeApp.swift), line 1108; [controller](../spark_serve_controller.py), lines 599–610 and 828–877. No live request was intentionally interrupted in this audit.

6. **Medium — Readiness does not test the client's network path.** vLLM probes run curl over SSH on the Spark, so a successful self-probe can coexist with Mac DNS/routing failure. `use` trusts that observation. Today's independent Mac checks passed, but the design still lacks this control. Keep rank/model identity checks and add a separate bounded client-origin probe; represent server health and client reachability independently. YuE already probes from the Mac. Evidence: [CLI](../spark-serve), line 585; [controller](../spark_serve_controller.py), line 714.

7. **Medium, dependent on network trust — Container privilege and API access are broader than necessary for every recipe.** All three inherit privileged mode, host network/IPC, RDMA device access, and a writable HF cache; all bind to all interfaces without a configured API key. Readiness also lacks credential support, so enabling API authentication alone would break that path. Make privileges recipe-specific, qualify narrower access for solo models, split read-only weights from writable runtime caches, and support environment-supplied credentials consistently. Host networking/RDMA may remain necessary for distributed execution. No public exposure or exploit was established; the finding is excessive common privilege and an undefined access boundary. Evidence: [CLI](../spark-serve), lines 136–175, 585 and 1112; [catalog](../models.example.toml).

8. **Medium — Current evidence does not establish sustained reliability or a fair quality ranking.** Historical results use different workloads, reasoning modes, output lengths, and rate definitions. DS4 has decode measurements, Qwen's principal speed numbers include prefill with thinking disabled, and Nemotron's number is a single thinking-enabled smoke. They cannot fairly rank models. The DS4 prefill script also uses a wall-clock seed and prints totals without saving exact prompts/runtime identities. Add a shared versioned corpus, reproducible requests, correctness checks, and per-run provenance. Evidence: [DS4 recovery](ds4-startup-recovery.md), [Qwen qualification](qwen38-nvfp4.md), [Nemotron qualification](nemotron-super.md), [prefill tool](../tools/ds4_prefill_bench.py).

9. **Low to medium — The normal verification path omits most tests.** README advertises unittest discovery, which ran 96 tests; pytest ran 345 plus 32 subtests. Document the complete command and reproducible test dependencies. Add CI or an equivalent required local check, including GUI state fixtures and catalog validation. This is a verification-process gap, not a failure in today's full suite. Evidence: [README](../README.md), line 252; [tests](../tests).

10. **Low — Product information and repository hygiene lag the implementation.** Model cards clip task-relevant notes, including Qwen's long cold start, while showing internal wrapper terms. The README still promises a YuE card after its deliberate September 19 removal. `.gitignore` excludes `models.toml` but not the currently untracked `models.toml.bak-*` files, making a broad add capable of including private host settings. Reconcile documentation, expose capability/startup/preparation information, and protect private backups. Evidence: [SwiftUI](../gui/SparkServeApp.swift), line 1344; [README](../README.md), line 190; [.gitignore](../.gitignore); commit `69a13ea`.

**Controls worth preserving**

The Python controller remains the lifecycle authority behind the thin SwiftUI process wrapper. Atomic state writes, nonblocking transition locks, per-node generation fencing, immutable container receipts, distributed-allocation protection, foreign GPU workload checks, and bounded diagnostics are substantive protections. Qwen/Nemotron preparation pins sources and verifies weights; their offline startup preflight runs before stopping the current service. Historical worker-only operations preserved the peer workload and protected database. These existing patterns should govern any new backend.

**Screenshot assessment and proposed interaction changes**

The screenshot clearly distinguishes selected versus running models and tells the operator that DeepSeek occupies both Sparks. The separate host panels and explicit Use in Hermes action fit independent serving well. The main usability defect is action meaning: an already running model still invites Start, and “Stop both Sparks” actually stops managed workloads, while “Restart Sparks” reboots machines.

Use “Stop workloads on both Sparks” and “Reboot both machines…” for those distinct operations. For a shared allocation, show one primary allocation action and a compact explanation in the worker panel instead of two prominent disabled controls. Put capabilities, tested context, preparation state, and expected startup time on each card; put wrapper names and MTP/KV tuning in details. Surface last successful observation and client/model match. Keep GPU memory, active requests, and startup stage available in expandable details. Verify minimum-width layout, keyboard traversal, VoiceOver, and high-contrast mode. Screenshot inspection alone does not establish numeric contrast or accessibility compliance.

**Why GLM-5.3-Flash NVFP4 is the recommended research candidate**

NVIDIA's support matrix, last updated September 19, explicitly lists **two GB10 DGX Sparks, NVFP4, and a 208GB NGC artifact**. This is stronger deployment evidence than a generic “fits in 256GB” calculation. The systems have separate memory spaces; the workload must fit per rank and communicate across the fabric. [NVIDIA support matrix](https://docs.nvidia.com/nim/vision-language-models/latest/support-matrix.html), [DGX Spark hardware](https://docs.nvidia.com/dgx/dgx-spark/hardware.html).

GLM has 320B total parameters, 18B active, visual input, and an MIT model license. Its published DeepSWE score is 63.4. Z.ai's evaluation uses a 400K context and six-hour timeout. [Upstream model card](https://huggingface.co/zai-org/GLM-5.3-Flash).

For comparison, Qwen Flash-Next reports DeepSWE 58.7, selecting its best of two harnesses at 256K context; its table gives DeepSeek-Flash-0731 54.4. That is directional evidence, not a controlled comparison with the exact original Flash revision installed here. Qwen also uses one Spark in this bundle, which remains a major throughput and flexibility advantage. [Qwen model card and evaluation settings](https://huggingface.co/Qwen/Qwen3.8-Flash-Next).

NVIDIA's September 9 quant release reports GPQA 92.11 versus BF16 92.17, MMMU-Pro 76.30 versus 76.88, and Terminal-Bench 2.1 83.15 versus 82.58. These suggest small quantization effects under its evaluation settings. Its generic vLLM example uses four GPUs and cannot itself establish dual-Spark operation. [NVIDIA GLM quant card](https://huggingface.co/nvidia/GLM-5.3-Flash-NVFP4).

NVIDIA's Nemotron Super quantization notes report NVFP4 GPQA without tools at 79.23. This supports investigating a higher reasoning tier, but differing evaluations and runtime settings prevent a clean head-to-head claim. No retrieved evidence establishes GLM dominance across all three local profiles. [Nemotron quantization evaluation](https://github.com/NVIDIA-NeMo/Nemotron/blob/main/docs/nemotron/super3/quantization.md).

| HF checkpoint | `nvidia/GLM-5.3-Flash-NVFP4` |

Sources: [pinned HF tree](https://huggingface.co/nvidia/GLM-5.3-Flash-NVFP4/tree/09b04e5e74bca08ca8549fc736d4cdd8624bfde3), [metadata API](https://huggingface.co/api/models/nvidia/GLM-5.3-Flash-NVFP4?blobs=true), [pinned configuration](https://huggingface.co/nvidia/GLM-5.3-Flash-NVFP4/blob/09b04e5e74bca08ca8549fc736d4cdd8624bfde3/config.json).

Each live host exposed 121.688 GiB total RAM. Subtracting an ideal 95.199 GiB shard share leaves about **26.49 GiB per host** before OS, duplicated weights, activations, caches, and loading transients. This is a rough inference, not measured GLM headroom. Existing DS4 would have to release its allocation. The 208GB NGC artifact and 204.439GB HF weights are distinct quantities; byte identity or interchangeability was not established.

The official two-Spark NIM guide starts rank 0, obtains `NIM_PRIMARY_NODE`, then starts rank 1. Rank 0 serves clients. It uses RoCE devices and unlimited memlock, and explicitly delegates transport discovery to its helper rather than manually setting transport variables. Video needs FFmpeg 8. Its connected example uses an NGC key and also documents offline deployment. These differences require a backend adapter, not just a new TOML entry. [NVIDIA two-Spark deployment](https://docs.nvidia.com/nim/vision-language-models/latest/deploy-on-dgx-spark.html).

Model and runtime licensing are separate: NIM links to NVIDIA's AI Product Agreement. Check access for the exact image/model artifact; generic documentation allows some public images without a key, while other artifacts require credentials. Do not infer that a paid license or universal keyless access is required. [NIM agreement](https://docs.nvidia.com/nim/vision-language-models/latest/EULA.html), [installation](https://docs.nvidia.com/nim/vision-language-models/latest/get-started/installation.html).

Community implementations provide useful precedent but are not interchangeable with the official lane. An older two-Spark recipe reports roughly 20–30 tok/s and a long startup using a different quantization/runtime and text-only workarounds. A newer SparkGLM lane labels itself a source preview, records an attention approximation, and has a separately licensed speculative draft. None of those numbers is a promise for NIM on this pair. [Operator recipe](https://github.com/kingjones30/GLM-5.3-Flash-2x-DGX-Spark), [SparkGLM limitations](https://github.com/Enntity/sparkglm).

**Implementation sequence and acceptance gates**

| Sequence | Concrete work | Completion evidence |
|---|---|---|
| 1. Correct trust and transition gaps | Mandatory recipe validation, DS4 pins/preflight, stale-observation state, model-aware Hermes badge and atomic config writes | Malformed recipes cause zero remote mutations; status failures never claim fresh readiness; same-URL model swaps show correct client state |
| 2. Make operations clear | Idempotent Start or explicit Restart model, vLLM drain/force distinction, Mac-origin checks, updated labels/test instructions/private-backup ignores | Fake-CLI GUI fixtures; bounded status failure behavior; full offline suite and native checks |
| 3. Implement an experimental NIM adapter | Preserve existing allocation locks/labels/immutable receipts; implement NIM rank order/handshake; isolate its transport settings; define endpoint identity, stop/log handling, two-rank health, and credential redaction | Offline lifecycle/failure tests and preflight on both nodes before any switch; exact artifact/image identities recorded |
| 4. Qualify on hardware | Capture existing baselines, load GLM, test actual task quality, memory, startup, endpoints, and recovery; preserve a verified baseline restore path | Same corpus and budgets across models; complete receipts; successful return to DS4 or independent models |
| 5. Promote conditionally | Add normal catalog/UI status only after it has a demonstrated benefit | Better task completion at acceptable latency, no critical interface regressions, and acceptable sustained operation |

For the comparison, use a frozen practical corpus with two equally weighted tracks:

| User priority | Proposed tasks | Required evidence |
|---|---|---|
| Coding and tool use in Hermes | 30 repository coding/debugging tasks plus 20 multi-turn tool workflows | Executable tests pass; edits stay within task scope; tool names, arguments, and result IDs are valid; the agent recovers from a failed tool call; streaming and reasoning/final separation work through the actual Hermes client |
| Multimodal work and long documents | 25 document tasks plus 25 visual or mixed document/image tasks | Correct answers with source locations; cross-section synthesis and contradiction handling; chart/table interpretation, scanned-page reading, and screenshot/diagram understanding; original visual inputs survive the actual client-to-server path |

Qwen is the principal existing multimodal baseline. DS4 is the principal existing long-context text baseline; Nemotron remains in the common coding/tool/text comparison. Report both the common text subset across all models and capability-specific results; do not silently score a text-only profile on vision. Keep tasks within each profile's qualified context for matched comparisons, and separately report the longer-context capability ladder. A vision-enabled server does not establish that the actual Hermes client correctly delivers images; verify that interface explicitly.

Run at least three repetitions, keep prompts/context/harness/output budgets comparable, record model-specific reasoning controls, and score correct task completion plus total wall time. Syntax-only coding checks and single-marker document retrieval are insufficient. These sample sizes are proposed pilot choices, not a statistical guarantee of superiority. Record the opportunity cost of occupying both Sparks versus the existing independent-model configuration.

Measure p50/p95 first-token and completed-task latency, prefill and decode separately, C1 and C2 aggregate throughput, errors, peak memory, swap deltas, thermal/power behavior, and cold/warm startup. Start context qualification at 32K, then 128K/262K; extend to 512K/1M only with retrieval/reasoning checks and enough memory. An architectural limit or successful four-token response is not a quality qualification.

Require repeatable cold and warm starts, a multi-hour mixed-load soak, successful worker-loss cleanup/recovery during a planned test window, and verified restoration of an existing profile. Proposed quality promotion criterion: at least a 10 percentage-point gain on one priority track or a comparably useful reduction in time to a correct answer, with no material regression on the other track and no critical tools/streaming/JSON/Hermes regressions. Report both track results independently so a coding improvement cannot hide degraded document or visual performance. Assess uncertainty and enlarge the corpus if the result is marginal. A model that improves only one track can remain an optional specialist, rather than replacing the existing general choice; occupying both Sparks must earn its cost.

Confidence is high in the current offline test result and the existence of NVIDIA's supported GLM topology; moderate in source-based fault predictions; limited for sustained service and workload-specific model superiority. The recommended next engineering work is the trust/preflight correction followed by the isolated GLM pilot described above.
